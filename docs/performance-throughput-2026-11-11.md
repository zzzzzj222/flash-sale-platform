# 后台吞吐优化与复测

## 2026 年 11 月 11 日实现与参数

本轮在活动优先锁序修复基础上，完成投递退避、查询复用、同活动小批次事务、批量 SQL 与独立结果同步。生产配置需根据端到端排队和处理 P99、故障检测及业务期限校准，以下为本项目的默认值。

| 项目 | 当前实现 |
| --- | --- |
| 生产端批次 | 同租户、同活动最多 16 个申请，兼容旧单条消息 |
| 领取租约 | 30 秒，使用令牌防止旧回调改写新租约 |
| 发布失败 | 1、2、4、8、16、30 秒退避，上限 30 秒，加入 20% 抖动 |
| 发布已确认、等待业务结果 | 15、30、60 秒退避，上限 60 秒，加入 20% 抖动 |
| 业务排队期限 | 下一次处理时间截断到业务期限，到期后由独立执行器直接落库判断 |
| 到期处理失败 | 按失败退避继续恢复，期间保留 pending 与预扣 |
| Redis 同步 | 每轮最多 64 个事件，按租户批量核对，缺失版本使用一次 Lua 同步 |
| 同步调度 | 每轮完成后等待 50ms，领取及完成标记批量更新并校验租约 |
| 有界执行器 | 发布 16 线程、队列 128；到期 4 线程、队列 32；Redis 同步 4 线程、队列 64；通知 4 线程、队列 16 |
| 索引迁移 | V4 增加 Outbox 按目标、状态、时间扫描的索引 |

`REQUEST_PUBLISH_WAIT_MS` 调整已确认发布后的初始等待，`REQUEST_CLAIM_LEASE_MS` 调整领取租约。30 秒排队活动在期限到达时进入超时处理，重投等待遵守业务期限。Broker 发布确认与消费完成分别处理，消费者在数据库事务成功返回后确认消息。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

消费事务一次取得活动锁，批量插入申请并用一次当前读取得各申请状态，批量创建、锁定用户额度，在内存中按组内顺序决定结果。库存采用一次条件更新，额度和申请状态分别用批量 SQL 写入，Redis 同步事件和可选 Webhook 同事务批量插入。后续处理复用读到的记录与结果。

提交后立即尝试一次批量 Redis 同步，失败由持久 Outbox 恢复。同步程序批量读取并跳过已经同步的相同版本，减少重复 Lua 写入。已离开排队且同步完成的重复消息直接返回，首次入口拒绝仍建立持久化记录和同步事件。

## 批次失败边界与验证

新版消费兼容历史单条对象，新增批量数组格式。部署顺序先完成消费者升级，再启用新版批量发布，避免旧消费者拒绝数组消息。

- 售罄、累计限购及排队超时按申请记录 REJECTED，其他申请继续处理，批次可正常提交。
- SQL 等技术异常使该小批次的库存、额度、申请、事件一起回滚，容器重试该消息。最多 16 条限制单次故障的重试范围。
- 数据库已提交后的 Redis 同步或 Webhook 故障由 Outbox 补偿。提交成功后的消息确认丢失由请求幂等处理。
- 提高批量和并发会扩大回滚范围，并增加资源争用的可能性。执行器容量、批量上限、统一锁序、幂等和租约校验约束这些风险。

最终执行 `mvn -s ../scripts/maven-settings.xml -B -ntp clean verify`，9 项单元测试和 28 项集成测试全部通过，无失败、错误或跳过。新增回归覆盖混合业务结果、批量技术故障整体回滚及重试、真实 RabbitMQ 数组批次与旧消息兼容、已提交批次的 Redis 故障恢复、退避抖动和业务期限、旧回调令牌隔离、Outbox 过期租约无法覆盖新租约。整体回滚用例在 Outbox 插入时注入数据库约束异常，确认前面已执行的库存、额度及申请写入全部撤销。

## 压测环境与统计口径

复用上轮 k6 脚本、机器及参数，使用独立 Compose 项目 `flashsale-throughput-20261111` 和全新持久卷。主机为 Windows 11、i9-11900H、16 逻辑核、约 32GB 内存。单 JVM 使用 Java 25、1GB 最大堆，数据库池 16、消费者 2～4、prefetch 8。MySQL 8.4、Redis 8.2、RabbitMQ 4.2 为单节点 Docker；Redis AOF 每次同步、noeviction。Webhook 在压测中关闭，回调重试由集成测试验证。

正式场景共 9 个，另有两次 20/s、5 秒预热。常规活动库存 100 万，限购 1，排队期限 30 秒、预占期限 1800 秒。除接入方限流对照外，入口全局和接入方限流均提高至 20000/s。k6 与服务同机，200 预分配 VU、最大 500 VU，主机同时运行 OpenSearch 与 Chroma。版本、完整参数、JAR 和业务源码 SHA-256 保存在 [JSON 汇总](../load/results/2026-11-11-throughput-summary.json)。

受理 P95 衡量 HTTP 202。成功预占 P95 使用 SQL 的 updated_at_ms 减 created_at_ms，包含预扣后等待投递与数据库处理，仅统计最终 RESERVED 的申请。每批共用锁定后的数据库时间裁定状态。混合场景每次提交后读取一次活动和一次申请结果。每轮等待所有申请落库、台账同步、Outbox 和主队列清空后再核账。恢复等待包含采样和 RabbitMQ 管理指标刷新开销。

RabbitMQ ready/unacked 和 QUEUE_LIMIT 按消息条数统计，一条消息承载 1～16 个申请；Redis pending、HTTP 202 和数据库记录按逻辑申请统计。入口 REJECTED 保存原判定时间，其状态时间差可为 0，不能代表落库延迟。

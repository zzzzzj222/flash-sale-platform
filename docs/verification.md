## 自动化验证

`mvn verify` 使用独立 Testcontainers 容器启动 MySQL 8.4、Redis 8.2 和 RabbitMQ 4.2。包含 1 项签名单元测试与 13 项端到端集成测试。

| 场景 | 断言 |
| --- | --- |
| 64 个用户并发争抢 10 份配额 | 10 条有效预占，54 条拒绝，剩余配额为 0 |
| 同一个请求并发重复提交及重复消息 | 仅保存一条请求，只扣减一次配额 |
| 同一用户并发提交多个请求 | 总预占量符合活动限购 |
| 用户编号大小写 | 不同编号保持独立，适用于数据库默认不区分大小写的环境 |
| 跨接入方访问及权限 | 记录隔离，业务管理与全局运维权限分开 |
| 成交确认 | 相同订单可重复确认，订单冲突与成交后取消被拒绝 |
| 预占到期 | 配额与限购名额归还 |
| 付款晚到 | 已到期预占无法确认，释放结果持久化 |
| 排队期间取消或到期 | 后续消息无法再次扣减库存 |
| RabbitMQ 暂停 | 请求先持久化，投递失败后恢复处理 |
| Redis 暂停 | 返回 503，数据库未创建请求 |
| 业务通知 | 签名正确，失败重试保留事件编号，支持人工重投 |
| 参数及幂等冲突 | 无效参数和复用编号时的参数变化被拒绝 |

前端通过 TypeScript 检查和 Vite 生产构建。小程序请求封装使用 `miniprogram-api-typings` 进行 TypeScript 严格类型检查。OpenAPI 文档与 Compose YAML 已解析检查，k6 脚本已通过 `inspect`。

## 本机基础负载

独立 `partner` 接入方创建 100 份活动配额。k6 使用恒定到达率 100 次/秒、持续 10 秒，预分配 50 个虚拟用户，实际使用约 2 至 7 个。该场景衡量 HTTP 受理接口。

| 指标 | 实测 |
| --- | --- |
| HTTP 请求总数 | 1001 |
| 202 受理 | 1001 |
| HTTP 失败率 | 0% |
| 平均受理耗时 | 32.95 毫秒 |
| P95 受理耗时 | 56.04 毫秒 |
| 最终有效预占 | 100 |
| 最终售罄拒绝 | 901 |
| 活动剩余配额 | 0 |
| 用户限购占用量合计 | 100 |

负载结束后通过数据库查询核对状态、库存和限购。受理耗时与最终获得预占的耗时属于不同指标。原始摘要位于本机 `.runtime/k6-summary.json`。

该结果适用于本机配置与本次工作负载。几百或几万同时请求、多实例、高可用集群、跨机故障恢复、长期运行、真实微信登录与真实支付尚需独立验证。Dockerfile 提供构建方案，当前运行与验证使用本机 JAR。

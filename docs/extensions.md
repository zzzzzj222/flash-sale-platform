# 扩展需求与实施边界

以下均为待实现或待验证的扩展方向，不是当前已交付功能。优先级是建议顺序，可根据业务场景调整；本次开源只整理需求，不新增这些功能。

## 推荐扩展顺序

| 优先级 | 扩展需求 | 改动位置与约束 | 最小验收标准 |
| --- | --- | --- | --- |
| P0：正式接入前 | 真实用户与资格 | 在业务后端实现登录、资格和请求归属校验；复用现有 `/api/v1`；前端不能指定任意可信用户或携带接入密钥 | 越权读取、取消和冒用用户失败；同一用户跨渠道共用限购 |
| P0：正式接入前 | 真实订单与支付 | 业务后端完成下单、金额/商户/订单验签、确认与对账；不在秒杀核心直接接支付 SDK | 重复支付通知只完成一次履约；下单失败释放；付款晚到可退款并留存补偿记录 |
| P0：正式接入前 | 生产部署与恢复 | 部署层配置 TLS、访问控制、独立运维身份、密钥管理、备份和告警；关闭演示入口 | 外部无法访问演示接口；恢复备份后核对库存/限购；故障重启不重复扣减 |
| P1：数据增长时 | 活动/记录分页与归档 | 扩展 `SaleController`、`SaleService`、`SaleStore` 和 OpenAPI；当前活动列表最多 100 条，演示记录最多 30 条，无正式用户记录列表 | 游标排序稳定；跨接入方不可读；归档不丢失幂等依据和未完成事件 |
| P1：运维需要时 | 活动管理 | 当前没有修改、暂停、提前结束或补库存接口；先确定活动生命周期、存量预占及审计规则，再扩展 Contracts、Service 和迁移 | 规则变更与并发抢购互斥；配额守恒；原有预占按明确策略处理 |
| P1：业务需要时 | 退款与回补 | 当前 `CONFIRMED` 为终态；需定义独立退款/回补契约、可回补上限和幂等编号 | 重复或部分退款不重复增加库存；支付、履约和配额可对账；不能复用 release 撤销成交 |
| P1：规模增长时 | 监控与性能验收 | 复用 `OperationalMetrics`、Prometheus 和 `load/flash-sale.js`，补充热点、多活动、轮询、排队延迟和长稳场景 | 给出机器配置、流量模型、阈值与最终库存核对；报告受理和最终预占两种耗时 |
| P2：压测证明需要时 | 热点库存吞吐 | 目前同一活动行锁串行化库存事务；先压测，再评估配额分片、路由与对账，保持库存和用户限购一致性 | 单热点吞吐达到目标，同时无超卖、无超限、无重复归还，故障后可核对恢复 |
| P2：票务需要时 | 选座、连座或多资源组合 | 新增资源模型、预占策略、统一锁顺序和数据库迁移；现有 quantity 不能表达座位或多个资源的原子预占 | 同座位不能重复预占；组合要么全部成功，要么全部回滚；取消/到期全量归还 |
| P2：治理需要时 | 接入方管理与密钥轮换 | 当前接入方列表由部署配置加载；动态管理需认证授权、审计、双密钥过渡与失效机制 | 轮换期间旧新密钥按策略有效；撤销后不可访问；业务管理员不能获取全局权限 |
| P2：部署规模需要时 | Spring Cloud 与服务拆分 | API 与处理实例已有 `WORKERS_ENABLED` 开关；网关、发现、配置中心及独立通知进程仍需建设 | 多实例重复投递安全；入口隔离与限流生效；拆分不破坏库存/限购/预占事务边界 |

## 扩展接口必须满足的要求

1. 先在需求中说明调用方、资源归属、权限、幂等编号、合法状态与失败补偿，再确定路径、字段和 HTTP 状态。
2. 保持 `/api/v1` 已有语义；改变状态含义、必填字段或响应结构时明确兼容策略，必要时新增版本。
3. 接入方从认证信息取得，用户身份由可信业务后端注入。新增表、索引、查询和事件都必须保留接入方隔离。
4. 库存、限购与预占在现有事务边界内变化；产生外部事件时通过同事务 Outbox 登记，接收方继续幂等。
5. 数据结构变更使用新增 Flyway 迁移，保留已有迁移；同时修改 Contracts、Controller、Service/Store、OpenAPI 和受影响的调用端。
6. 增加与实际风险对应的集成测试：权限、并发、重复请求、重试、确认与超时竞争、故障恢复，以及库存/限购守恒。

## 提交扩展需求时提供的信息

在 GitHub Issue 中说明：业务场景与现有流程缺口、预计流量与热点分布、调用方与数据归属、建议接口示例、状态变化、失败处理、验收标准及兼容要求。不要附真实密钥、支付凭据或用户个人信息。

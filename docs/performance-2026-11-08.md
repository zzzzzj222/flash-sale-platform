# 2026-11-08 本机阶梯负载与过载测试

本次完成了默认限流、持续负载、提高准入限额后的过载、短时突发、少库存争抢和恢复检查。结论是：本机在 75 次/秒、60 秒的场景下保持短队列；100 次/秒已出现积压。HTTP 受理可以远快于后台完成预占，不能把返回 202 的吞吐当作可持续抢购能力。

目标 2000 次/秒的突发测试没有达到目标速率。最高一轮的实测平均 HTTP 受理约 815 次/秒，同时存在压测端未发出的迭代和大量业务排队超时。这是本环境的观测值，不是服务的绝对上限，也不能证明支持 2000 或几万并发。

使用 `partner` 身份，不启用 Webhook；压测内容为创建活动后提交抢购，未混入查询轮询、支付、成交确认或取消。不同请求使用不同用户编号，本轮验证库存及限购占用守恒，不单独验证同一用户的恶意并发绕过场景。各轮在同一个独立测试库累积数据，均先等待上一轮离开排队状态，再开始下一轮。

初轮发现宿主终端有 `DEBUG=release`，使 Spring Boot 开启调试日志。初轮数据保留在本机，但不进入下表。正式结果显式使用 `DEBUG=false`、`TRACE=false` 和根日志级别 INFO；未修改宿主全局环境或项目默认配置。

“实际 HTTP/s”使用 k6 报告的平均速率，包含完成在途请求的尾部时间。“受理 P95”只统计返回 202 的 HTTP 请求。“预占 P95”从数据库 `created_at_ms` 到进入 `RESERVED` 的 `updated_at_ms` 计算，仅包含成功预占的请求，不包含前置网络/认证及后续支付、客户端轮询。超时失败另列，避免用成功样本掩盖失败。

## 实测结果

| 场景 | 目标速率 / 时长 | 实际 HTTP/s | 202 / 429 | 受理 P95 | 最终预占 / 排队超时 | 预占 P95 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 提高限额，持续负载 | 75/s，60 秒 | 75.00 | 4500 / 0 | 60 ms | 4500 / 0 | 364 ms |
| 默认限流，持续负载 | 100/s，30 秒 | 99.92 | 3000 / 0 | 66 ms | 3000 / 0 | 4.91 s |
| 默认限流，较高负载 | 500/s，20 秒 | 499.99 | 4000 / 6001 | 179 ms | 4000 / 0 | 21.66 s |
| 提高限额，过载 | 500/s，20 秒 | 498.84 | 10001 / 0 | 158 ms | 2152 / 7849 | 28.94 s |
| 提高限额，500 VU 突发 | 2000/s，5 秒 | 698.41 | 3973 / 0 | 847 ms | 2958 / 1015 | 28.76 s |
| 提高限额，1000 VU 突发 | 2000/s，5 秒 | 814.85 | 5088 / 0 | 1.39 s | 2816 / 2272 | 28.86 s |
| 过载恢复后的负载 | 75/s，20 秒 | 74.83 | 1501 / 0 | 84 ms | 1501 / 0 | 1.52 s |

75/s 的 60 秒场景采样队列峰值 25；100/s 的 30 秒场景采样峰值 444，末段仍在增长，停止提交后才清空。因此，75/s 只是本轮的短时稳定观测点，100/s 不能据此当作持续容量；恢复后的延迟也比前一轮 75/s 更高，仍需长稳和重复试验。

默认限流的 500/s 场景中，4000 个请求在 20 秒内受理，符合单接入方 200/s 限额。其余 6001 个返回 429，这是限流行为，不是抢购成功。提高限额后的 500/s 场景有 **78.48%** 的已受理请求最终排队超时，尽管 HTTP 层没有非预期状态，业务处理已经过载。

两轮目标 2000/s、5 秒的场景分别有 **6027** 和 **4912** 个 `dropped_iterations`：这些操作根本未从 k6 发出，不计入服务端失败，也不能算成服务成功处理。提高 VU 后响应变慢、吞吐有所增加，当前同机压测和有限 VU 仍会影响结论，不能据此定位绝对硬件上限。

## 正确性与恢复

额外创建仅 100 份库存的活动，以 200/s 持续 5 秒提交 1001 个请求。最终 100 个 `RESERVED`、901 个 `REJECTED/SOLD_OUT`，剩余库存 0，限购占用合计 100，单用户最大占用 1，没有超卖。

所有正式场景在离开排队状态后核对：

```text
总库存 - 可用库存 = RESERVED/CONFIRMED 数量合计 = 用户限购占用合计
可用库存 >= 0
单用户限购占用 <= 活动限购
数据库请求数量 = k6 统计的 202 数量
最终 QUEUED 数量 = 0
```

以上断言全部通过。本轮正式场景没有观察到非 202/429 的 HTTP 状态，也没有触发 5 秒请求超时；“没有 HTTP 错误”不代表没有业务排队超时。

过载后保留后台处理，最终排队记录全部离开 `QUEUED`，再测 75/s、20 秒，1501 个请求全部预占成功。临时服务与本轮三个测试容器在测试后停止，命名卷和本机原始结果保留，未删除或改写原项目的数据库卷。

## 暴露的容量风险

1. **受理能力与完成预占能力不匹配。** 限流只按固定请求频率计数，未根据数据库排队数量或最老请求年龄自适应减流。默认单接入方 200/s 也高于本机本轮稳定观测点，长时间使用需结合实际 SLA 调整并复测。
2. **主要积压出现在数据库 Outbox。** 默认 500/s 场景曾采到 2336 条 READY 事件，而 RabbitMQ ready 消息约 81 条。`OutboxService.claim()` 每批最多 16 条，`OutboxDispatcher` 等整批完成后再延迟 100 ms 调度。仅按固定延迟计算，长期调度上界约为每实例 160 条/秒，加入数据库、发送确认等开销后还会降低。这是优先测量与调优的路径，不代表已排除数据库热点锁和磁盘等因素。
3. **队列期限不保证状态准时更新。** 提高限额后的 500/s 场景中，排队失败记录从创建到更新最长约 **95.17 秒**，明显超过 30 秒的配置期限。处理与确认仍校验有效期，但后台过期扫描和队列消费在过载时会延后把记录标记为终态，影响用户等待与查询体验。
4. **RabbitMQ 长度上限不是数据库排队请求上限。** `QUEUE_LIMIT` 约束 RabbitMQ 队列，尚未投递的请求与事件仍可在 MySQL 累积；不能只看 MQ 队列长度判断系统没有积压。

下一步应先为“预占处理 P95、排队超时率、最长等待时间”确定目标，再测量 Outbox 批处理、调度开销及热点锁等待，补充基于积压的准入与过期处理验收。需要更高流量时，将发生器与应用分机，分别测试单热点、多活动和混合查询；本次没有直接修改这些业务实现。

## 复测方法与证据

聚合数据、活动编号、库存核对、请求数量及延迟记录见 [JSON 汇总](../load/results/2026-11-08-summary.json)。本机原始 k6 摘要、日志与采样位于 `.runtime/load-2026-11-08/`，属于被 Git 忽略的本地文件。`raised-500` 的初次恢复观察窗口不足，之后继续等待并从数据库补采终态；表中 95.17 秒来自数据库时间，并非初次观察窗口的估计。

已为 [k6 脚本](../load/flash-sale.js) 增加非预期状态比例、202 专属延迟及停止阈值，并将 429 作为预期的限流响应。恒定到达率执行器不再在 429 后额外 sleep，避免发生器因等待占用 VU。脚本仍只测 HTTP 受理，最终结果与库存需另外核对。

复测应使用独立测试环境。先在 PowerShell 7 运行 `scripts/init.ps1`，加载 `scripts/env.ps1`，以独立 Compose 项目启动三项依赖，并在独立应用进程设置上表中的端口、限流和 JVM 参数。端口已被占用时需先准备独立端口映射。本轮未启用 Webhook；应用必须显式关闭 DEBUG/TRACE。服务运行后，在另一终端加载环境并创建当次活动：

```powershell
. ./scripts/env.ps1
$env:BASE_URL = 'http://127.0.0.1:18081'
$authBytes = [Text.Encoding]::UTF8.GetBytes('partner:' + $env:SALE_PARTNER_SECRET)
$env:AUTHORIZATION = 'Basic ' + [Convert]::ToBase64String($authBytes)
$headers = @{ Authorization = $env:AUTHORIZATION }
$activityBody = @{
    resourceId = 'load-retest'
    title = '独立压测活动'
    stock = 1000000
    limitPerUser = 1
    holdSeconds = 1800
    queueTimeoutSeconds = 30
    startsAt = [DateTimeOffset]::UtcNow.AddSeconds(-5).ToString('o')
    endsAt = [DateTimeOffset]::UtcNow.AddHours(1).ToString('o')
} | ConvertTo-Json
$activity = Invoke-RestMethod -Method Post -Uri ($env:BASE_URL + '/api/v1/activities') -Headers $headers -ContentType 'application/json' -Body $activityBody
$env:ACTIVITY_ID = $activity.id
$env:RATE = '75'
$env:DURATION = '60s'
$env:VUS = '200'
$env:MAX_VUS = '500'
New-Item -ItemType Directory -Path .runtime -Force | Out-Null
k6 run --summary-export .runtime/retest-summary.json load/flash-sale.js
```

调整档位前等待上一场活动排队结束并核对库存，为下一轮创建新活动；新一轮不要复用原活动。场景参数完整记录在 JSON 的 `scenario` 字段。k6 脚本在非预期 HTTP 状态比例达到 5% 时中止（10 秒后开始判定）；本轮额外用本机监视器在剩余物理内存低于 1500 MiB 时停止加压，这一内存停止线不内置于通用 k6 脚本，复测时需另行监视。

本次不是生产容量承诺，未覆盖长时间稳态、多机高可用、网络故障、真实支付、Webhook、用户轮询和几万真实并发用户。RPS、VU 与同时在线用户是不同指标，不能相互直接换算。

## 统计口径

- 受理 P95 统计 HTTP `202` 请求的耗时。`202` 包含入口判定为 `QUEUED` 和 `REJECTED` 的结果。
- 成功预占 P95 使用 MySQL 中 `RESERVED` 记录的 `updated_at_ms - created_at_ms`，包含 Redis 预扣后等待投递及数据库处理的时间。样本只包含最终预占成功的申请。
- 实际提交速率取 k6 的提交计数速率，包含在途请求的完成尾部。混合查询场景另有两倍查询请求，其总 HTTP 速率约为提交速率的三倍。
- 入口已经拒绝的申请保存入口判定时间，其数据库记录时差可以为 0。该值不能用作实际落库延迟。
- 每轮发压结束后继续等待 Redis 待投递数量、MySQL `QUEUED`、Outbox 待处理任务和 RabbitMQ 主队列消息清空，再核对数据。恢复等待包含约 3～5 秒的采样、管理指标刷新和检查开销。
- 各轮在同一独立测试库累积数据，随后切换接入方限流配置时重启了测试 JVM。表中数值属于本机短时观测，需要长稳和重复试验才能进一步确定容量。

## 死锁证据

本轮独立 MySQL 的 `information_schema.INNODB_METRICS` 中，`lock_deadlocks` 最终累计 114517 次，包含正式场景及两个预热场景。200/s 时保存的 InnoDB 日志记录了以下冲突。

```text
事务 1 持有 activities 同一记录的 S 锁，等待 X 锁
事务 2 持有 activities 同一记录的 S 锁，等待 X 锁
两个事务均在执行 SELECT ... FROM activities ... FOR UPDATE
InnoDB 回滚其中一个事务
```

该轮被测版本的消费事务先向具有活动外键的 `reservations` 插入记录，再申请活动行的排他锁。插入外键记录涉及父活动行共享锁，多事务随后升级锁时会形成上述等待环。排队到期申请也会执行这一路径，且可由 16 个投递线程并发调用，恢复阶段的冲突因此需要单独关注。[申请落库与活动锁定](../backend/src/main/java/com/flashsale/core/SaleService.java) · [投递和过期处理](../backend/src/main/java/com/flashsale/messaging/OutboxDispatcher.java)

死锁日志位于本机 `.runtime/load-2026-11-11/innodb-status-200.txt`，各场景的 k6 摘要、采样、最终核账和服务日志位于同目录。测试应用的业务代码使用上表提交版本，本轮增加了压测脚本的业务状态检查和计数。

## 活动行锁序修复与复测

### 修复内容

`SaleService` 在插入带活动外键的申请前，先对活动主键执行 `SELECT ... FOR UPDATE`。消费、旧消息处理、确认、取消和超时统一按活动、申请、用户额度的顺序加锁。后续处理复用已经锁定并读取的活动数据。库存条件更新、幂等参数检查、状态判断及 Outbox 继续在同一事务中执行。

取消与到期处理先用已有申请或 Redis 快照中的不可变活动编号定位活动，取得活动锁后通过 `FOR UPDATE` 重新读取申请。消费者在此期间已经提交并同步 Redis 时，处理逻辑使用数据库当前状态。Redis 中仍处于排队或入口拒绝的申请按需补齐数据库记录。

### 并发回归

新增共享锁阻塞下的并发落库回归，覆盖重复完整消息、旧消息、确认、取消及超时，断言所有事务完成、死锁计数增量为 0、库存与限购一致。该用例在旧代码上复现 `SELECT ... FROM activities ... FOR UPDATE` 死锁。另一个回归使取消事务先建立申请缺失的快照，再让消费者独立提交并同步 Redis，验证取消能取得最新记录并归还库存。

最终执行 `mvn -s ../scripts/maven-settings.xml -B -ntp clean verify`，9 项单元测试和 22 项集成测试全部通过，失败、错误及跳过均为 0。
